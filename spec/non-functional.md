# Нефункциональные требования

## Performance

- **Мгновенный отклик UI**: после тапа пресета основной фидбек (обновление списка/суммы) — в пределах одного кадра либо с минимальной задержкой; целевой горизонт — **логирование < 2 с** от намерения до подтверждения (визуального появления записи).
- **Старт приложения**: первая интерактивность после гидрации — приемлемо до ~1 с на слабых устройствах при умеренной истории; тяжёлые агрегаты не блокировать главный экран.
- **Главный экран** работает только с подходами за один день — объём данных мал.

## Offline-first

- Полная работоспособность без сети после первой загрузки приложения (PWA).
- Нет обязательных сетевых запросов в MVP.

## Надёжность хранения

- Персистентность в **IndexedDB** (не localStorage для массива подходов).
- Версия схемы в `meta` для будущих миграций.
- Обработка ошибок записи: пользователь видит понятное состояние; данные в памяти не расходятся с БД без явной стратегии (откат или retry).

## Безопасность и приватность

- Данные локальны; без передачи на сервер в MVP.

## Масштабируемость под backend

- **StorageAdapter** как единая точка обмена данными: позже реализация с REST/GraphQL и синхронизацией.
- Идентификаторы UUID совместимы с серверными.
- Разделение: доменные типы в `entities`, сеть — потенциально `shared/api` без изменения features.

## Доступность и UX

- Крупные зоны нажатия для quick-add; читаемые контрасты (тема уже в проекте).

## Edge cases (сводка)

Детали в `requirements.md`: двойные тапы, timezone/полночь, пустые данные, отсутствие рассинхрона с localStorage для домена, деградация при ошибках БД.
